# ROO — porting the 2026-10-12 review fixes onto `main`

**Date:** 2026-10-13
**Branch:** `fix/review-2026-10-12-port`, cut from `origin/main` @ `8bf017f` (v0.4.3)
**Worktree:** a dedicated git worktree, so the main checkout was never touched
**Companion documents:** [the original findings report](repo-review-2026-10-12.md) ·

---

## 1. Why this round existed

The 2026-10-12 review produced 118 records, of which 96 were confirmed by an adversarial
verifier, 8 stayed plausible and 14 were refuted. A fix round then wrote and locally
qualified corrections for them.

**Those fixes were never committed.** They existed only as uncommitted edits in a second
checkout, on branch `feat/authorization-revocation` @ `c412814` — 67 modified files plus
roughly 430 untracked ones. That branch is **20 commits behind `origin/main`** and holds no
commit `main` lacks. In the meantime `main` reached v0.4.3 and independently reworked the
HTTP and PostgreSQL case studies, so a textual three-way apply of the fix diff conflicts in
15 files.

So the fixes could not be merged. They had to be re-derived against `main`, finding by
finding. That is what this round did.

Two consequences shaped the whole effort:

- **The review was written against a dirty tree.** Parts of it describe content that never
  reached `main`: an "Academic position" section, a 13th design-review question, and a
  `research/literature.md` with 123 entries where `main` has 28. Findings resting on those
  are not defects on `main`. Each one had to be checked rather than ported.
- **The fix round deliberately avoided editing frozen files.** It wrote
  `CHANGELOG.revised-2026-10-12.md` and `agenda-revised-2026-10-12.md` rather than touching
  the originals, because those belonged to a release candidate under review. That constraint
  expired once `main` shipped three more releases, so this round edits in place — but only
  where a claim is actually wrong today.

## 2. How the work was organized

Ten parallel fronts, each owning a disjoint set of paths so they could edit one shared
working tree without colliding. Model choice followed the repository's cost-discipline rule:
Sonnet by default, Opus only where the reasoning was genuinely hard.

| Front | Model | Paths owned |
|---|---|---|
| http | Opus 5 | `case-studies/orders-payments/http/**` |
| java-mem | Opus 5 | `case-studies/orders-payments/java/**` |

Every front was told to **audit before fixing** and to classify each finding as
already-fixed-on-main, live, or not-applicable. Each was given the frozen fixed tree as a
*reference implementation* to port semantics from, never as a patch to apply. Each had to
verify with real commands and report real output.

I reviewed every diff myself rather than trusting the reports, and checked the specific
claims most likely to be wrong. Section 8 records what that caught.

## 3. P1 — code defects

### P1 #1 · Java `Store` was publicly constructible — capability leak

**Why it mattered.** `Adapters.Store` was `public static final class` implementing the public
`StorePort`. Any code in any package could build one and call `commit`, driving a `Paid`
order back to `Draft` and inserting a forged `RefundApproved` into the outbox. That breaks
the invariant `case-studies/orders-payments/SPEC.md:25-27` states.

**How it was fixed.** The concrete class became package-private. `commit` itself stays public
because it overrides a method on a public interface and Java forbids narrowing an override —
making the *class* unnameable is what closes the hole.

**Evidence.** Compiled against the pre-fix classes, an exploit in `package attacker` actually
ran and printed `forged state=Draft outbox=[Event[... kind=RefundApproved ...]]`. Against the
fixed tree the same source fails with `Store is not public in Adapters; cannot be accessed
from outside package`. A third negative-compilation sample,
`java/negative/ExternalStoreMutation.java`, now pins this in `build.sh`.

**I verified the hole is really closed**, not just narrowed: an outside subclass of
`InMemoryTemplateApplication` can widen the `protected store()` accessor, but it still cannot
obtain a real store, because constructing one requires the now-package-private class, and
Java forbids calling a protected member on an arbitrary instance from another package.

### P1 #2 · Java declined refunds left the order wedged

**Why it mattered.** `CompositionApplication.refund` and `TemplateApplication.refund` wrote
`Refunding` and only then threw, stranding the order in that state with no way forward.

**How it was fixed.** Both now return `Result.InvalidState` as the first statement when the
mode is `decline`, before any read or write. This mirrors what the Rust implementation
already did at `rust/src/application.rs:88`.

**Evidence.** Before: `refund threw: IllegalArgumentException`, `state after: Refunding`.
After: `refund returned: InvalidState`, `state after: Paid, refund intent=null`. The Java
unit-check count went from 280 to 296.

### P1 #3 · PostgreSQL Rust adapter had the same defect, caught only by a schema CHECK

**Why it mattered.** `Database::step` wrote the refund intention and then failed on SQLSTATE
23514, leaving a `Refunding` row behind.

**How it was fixed.** `Database::operation` now returns `Ok(Outcome::InvalidState)` for
`Action::Refund(_, Mode::Decline, _)` before any transaction opens. It deliberately runs
`assert_operation` and `check_authorization_scope` *first*, so a wrong operation or scope
still gets `Forbidden`.

**Evidence.** On a live PostgreSQL 18.6 an unfixed copy failed with 23514 and left the order
`Refunding` with `refund_id = r1`; the fixed code returns `InvalidState` and the order stays
`Paid` with no refund id. Two new Rust tests fail against the unfixed source.

**Deliberate trade-off, recorded.** A caller whose database grant was revoked now gets
`InvalidState` rather than `Forbidden` for a declined refund, because checking the stored
grant requires the transaction this fix exists to avoid. The review asked explicitly for
validation *before* the transaction, so the trade-off is inherent to the requested fix. It is
minimized by checking operation and scope first. For comparison, the Java PostgreSQL
implementation rejects `refund:*:decline:*` even earlier, at parse time, so the fix moves
Rust closer to Java rather than further away.

### P1 #4 · Java HTTP listener starved by slow clients

**Why it mattered.** 32 connections that sent complete headers and a `Content-Length` but
never sent a body pinned all 32 worker threads in the blocking body read. Later requests,
including cheap 404s, were never answered. The admission gate could not help because it was
acquired only *after* the body was read. With 96 or more stalled connections,
`CallerRunsPolicy` would additionally run the blocking read on the JDK dispatcher thread.

**How it was fixed.** `HttpProtocol`, `HttpService` and `HttpUnitTests` were reworked for a
body-read deadline with the body read under the admission gate.

**Status.** Code landed and building (`build.sh` exits 0, 154 protocol checks). The
end-to-end `http/verify.sh` qualification and the README/SPEC alignment were still in flight
at the time of writing; see section 10.

### P1 #5 · Every HTTP body-read error was reported as 413

**Why it mattered.** `main.rs` mapped *any* `to_bytes` error to `Fault::BodyTooLarge`, so
malformed chunked framing and a truncated body both answered `413 Payload Too Large`. A
client following the documented recovery protocol saw a size error for what was really a
framing or disconnect fault. Java closed the connection instead, so the two stacks diverged.

**How it was fixed.** A `body_fault` helper downcasts to
`http_body_util::LengthLimitError` for `Fault::BodyTooLarge` and falls through to
`Fault::InvalidRequest` otherwise.

**Evidence.** Unit test `body_read_errors_are_not_all_reported_as_oversize` asserts
`BodyTooLarge` for an oversized body and `InvalidRequest` for a truncated one. `cargo test`
passes.

### P1 #6 · The Rust HTTP server accepted URL fragments that Java rejected

**Why it mattered.** A cross-stack acceptance divergence contradicting the SPEC. httparse
accepts `#`, and `http`'s `PathAndQuery::from_shared` calls `src.truncate(fragment)`, so the
fragment was gone before routing could object. Java rejected the same target with 400 via
`uri.getRawFragment() != null`. `verify.py` had a query-string case but no fragment case, so
the gap was untested.

**How it was fixed.** `main.rs` now inspects the raw request line's second field for `#`
before `http::Uri` can discard it.

### P1 #7 · HTTP validation order differed between the two servers

The same request could get 406 on one server and 404 on the other, or 413 on one and 405 on
the other. `main` had already specified a single precedence in `http/SPEC.md` on its own, so
the remaining work was aligning the servers and the verifier to it. In flight; see section 10.

### P1 #8 · Track negative controls proved nothing

**Why it mattered.** The controls compared two fixed strings and therefore always returned
`rejected: true`, with `automatic_line_posts` as a literal. A dangerous mutation was
presented as rejected by the server when nothing had been exercised at all. This is the worst
class of defect in an evidence-producing repository: a control that cannot fail.

**How it was fixed.** The controls now send the injected action through the real PostgreSQL
runner and HTTP server and count the requests actually dispatched. The receipt key
`negative_controls` was replaced by `boundary_probes`; no consumer of the old key exists
outside the historical receipts in `research/`.

**Evidence, and this is the strongest check in the whole round.** The verifying agent broke
the server three different ways in a disposable copy and confirmed the control caught each one
with a specific diagnosis: a changed payment key accepted as `AlreadyApplied`; an
`IntentConflict` reported while the persisted `payment_id` was silently overwritten; and the
replayed line POST deduplicated. A control that fails when the behaviour it checks is broken
is the only kind worth having.

### P1 #9 · Container could forge its own exit status

**Why it mattered.** `track/compose.sh` read the run status from `container-exit-code.txt`
*after* `docker cp` had copied the container-writable evidence directory over the host one.
Code inside the container — the verifier, a pull request's modified tests, or learner starter
code — could write that file containing `0` and make the wrapper and the CI step report a
passing run. `container-isolation.json`, `image-platform.txt` and
`isolation-check-exit-code.txt` were overwritable the same way, and `DOCKER.md` presents
those receipts as binding a hosted run to its isolation boundary.

**How it was fixed.** The status now comes from `docker wait` on the host, cross-checked
against `docker inspect`. Container output is exported to a separate `container-evidence/`
directory, so it cannot overwrite host-generated receipts.

**Evidence.** A live container with a deliberately hostile entrypoint was run against both
versions. The fixed wrapper passes. The original `compose.sh` fails the same test in both
directions, reporting `0 != 7` and `9 != 0` — that is, it both reported success for a failed
run and failure for a successful one, once the container was allowed to write the file.

### P1 #10 · No CI job ran any of the four verifiers

**Why it mattered.** I confirmed this on `main`: `grep -rn "verify.sh\|regression.sh"
.github/workflows/` returned nothing. The 42-line oracle, the Java unit tests and the
negative compilation controls had never run hosted. The repository's strongest evidence was
produced only on one laptop.

**How it was fixed.** A new workflow `.github/workflows/orders-payments-base.yml` runs
`orders-payments/verify.sh`, `postgres/verify.sh`, `http/verify.sh` and `http/regression.sh`,
plus the download and evidence unit tests. It pins Rust 1.96.0, asserts the runner JDK is 21,
sets `PYTHONDONTWRITEBYTECODE=1`, and gives each PostgreSQL, HTTP and regression phase a
**distinct** `ROO_EVIDENCE_PATH` under `artifacts/roo-track/base/`, uploaded by an `always()`
step — so a hosted run can never overwrite the tracked historical receipts in `research/`.

**PostgreSQL 18 is installed explicitly** from the PGDG repository rather than taken from the
runner image, which carries only 16, with `create_main_cluster = false` so the packaged
cluster does not fight the verifier's private loopback one.

### P1 #11 · The root crate's only `cargo test` barely triggered

`authorization.yml` filtered `examples/` down to the single file
`examples/authorization_cases.rs`, so changing any other example ran no tests. Widened to
`examples/**`. `src/**`, `Cargo.toml` and `Cargo.lock` were already present on `main`.

### P1 #12 · An empty scenario name panicked the authorization example

**Why it mattered.** A fixture whose scenario column was empty reached
`coordinator.snapshot(id).expect("available").expect("seeded")` and aborted with exit 101 —
a panic where a fixture error belonged.

**How it was fixed.** The loop moved into a testable `run(input, out)` function; an empty name
returns `Err("invalid scenario: name must not be empty")`. The binary now exits 1 with empty
stdout and the message on stderr.

**Evidence.** Three new tests: two failed before the fix, one of them with the original
`seeded` panic; all three pass after. Output on the valid fixture is byte-identical before and
after, confirmed by SHA-256, which matters because other verifiers compare it to a fixed
oracle. The same bug existed in the Java twin `FixtureRunner.java` — it threw a
`NullPointerException` — and was fixed alongside, with a new harness check in
`authorization/verify.py` that asserts both runners reject the input with a diagnosed error.

### P1 #13 · The Rust consumer deduplicated on identity alone

**Why it mattered.** `Consumer::deliver` did `if self.seen.insert(event.id().clone())`,
ignoring content. A second event reusing a delivered `EventId` with *different* content was
silently swallowed instead of being detected as a conflict, while Java and PostgreSQL compared
the whole fact.

**How it was fixed.** `seen` became a `HashMap<EventId, usize>` pointing at the position of
the fact first delivered under each identity. An identical redelivery returns
`Outcome::RelayOk`; the same id with different content returns `Outcome::KeyConflict`, applies
nothing and keeps the first fact. `Store::relay` returns early on a conflict, leaving the
record unacknowledged. `deliver` now returns `Outcome` and is `#[must_use]`.

**I verified the parity claim** rather than accepting it: Java's `Consumer.accept` does
`applied.putIfAbsent(...)` then `if (old != null && !old.equals(event)) throw`, so it also
compares the whole event, and its exception propagates before `acknowledged.add(...)`. Both
implementations therefore detect the conflict and leave the event pending. The remaining
difference — Rust returns a typed outcome, Java throws — is the repository's existing,
documented cross-language asymmetry, not a new divergence.

**Evidence.** The new test
`relay_rejects_same_event_id_with_different_fact_and_keeps_it_pending` failed on the old code
with `left: RelayOk right: KeyConflict` and passes now. The case-study crate went from 20 to
22 unit tests.

## 4. Security and privacy

### The public repository leaked the author's local paths

**Why it mattered.** The origin is a public GitHub repository. Seven **already-tracked** files
embedded the author's absolute home-directory checkout path, and those files are copied into
published release sources: `research/http-checks.log`, `http-regression.log`,
`orders-payments-checks.log`, `orders-payments-run.md`, `postgres-checks.log`,
`postgres-regression.log` and `roo-compose-static-validation.json`.

This finding was **not in my original front assignments** — I found it in the review's
security appendix while the fronts were already running, and routed it to the research front
mid-flight.

**How it was fixed.** The absolute paths were rewritten to a `<home>/...` placeholder. Every
SHA-256 value was left byte-identical, because those hashes are the integrity anchors for the
historical runs, and no other content of the historical records was touched.

**Evidence, measured by me after the fact:**

```
git grep <absolute home prefix>           0 hits
git grep <codex session/attachment prefixes>   0 hits
```

The much larger leak the review described — 42 untracked files, around 75 session-transcript
references and 12 attachment references — lived in the `research/maad-roo-*` trees, which do
not exist on `main`. Not applicable here.

**And a guard so it cannot come back.** The review recommended adding a CI check for this and
no front did, which would have left the repository one careless paste from the same leak. The
new `scripts/check_local_paths.py` scans every tracked text file for three classes of
authoring detail: absolute home directories, assistant transcript or attachment paths, and
session identifiers. Recorded SHA-256 values are deliberately untouched, because those are the
integrity anchors a reader can actually verify. It runs in the documentation workflow, whose
path filters now cover both `research/**` and `scripts/**`, so editing the evidence or the
guard itself re-runs it.

It passes on 326 tracked text files — but a guard that has never failed is worth nothing, so
it was proved to fail. Three probes, one per class, were injected into a tracked file: each
was caught on the right line with its own specific remedy, and the exit status was 1. The
probe file was then restored byte-identically to its committed content. One deliberate
exemption exists, the guard itself, because it has to be able to name the patterns it forbids.

### Container resource limits

`compose.yaml` ran learner-edited Java and Rust plus the whole PostgreSQL and HTTP test stack
with no PID, memory or CPU limit, while `DOCKER.md` and the isolation check present the
container as an isolation boundary. A fork bomb or memory runaway could exhaust the host
Docker daemon, and the existing isolation check passed regardless because it only inspected
user, network, mounts, capabilities and `no-new-privileges`.

Now set: `cpus: 2.0`, `mem_limit: 4g`, `pids_limit: 256`, with a comment tying the values to
the `expected_*` assertions in `compose.sh`. **There is deliberately no disk limit** — the
writable layer has no portable quota — and that limit is recorded honestly in `DOCKER.md`
rather than implied away.

**Evidence.** The `expected_*` values in `compose.sh` were confirmed to match `compose.yaml`
(4 GiB, 2 CPUs, 256 PIDs), `docker compose config -q` exits 0, a live container passes the
extended isolation check, and removing `pids_limit` makes that check fail — so the assertion
is load-bearing rather than decorative.

### A pre-existing path bug that made the track verifier unrunnable at its own default path

`track/verify.sh` failed whenever the repository path contained a symlink, which on macOS
includes the ordinary `/tmp`. Reproduced against the original script: exit 1 with
`ValueError ... is not in the subpath of '/private/tmp/...'`. The current scripts exit 0
through `/tmp`, through `/private/tmp`, and through a `/tmp` symlink to the real repository.

## 6. P4 and P5 — documentation and tooling

### Tooling defects that were silently weakening the guards

- **`scripts/check_doc_examples.py` was not checking most examples.** It ignored blocks
  labelled `Rust` or `rs`, blocks fenced with `~~~`, blocks with four or more backticks, and
  indented blocks — and it scanned only `docs/*.md`. Unchecked examples passed as checked. It
  now recognises all those forms, fails on any Rust or Java fence not marked as tested, and
  scans all 62 published Markdown files. One excerpt block is exempted by path **and**
  SHA-256, so the exemption cannot silently widen.
- **`scripts/check_vocabulary.py` never scanned `src/`**, which is exactly why the stale
  concept groupings in `src/lib.rs:8` survived. It now scans `src/` and `examples/`. Its first
  run failed on `src/lib.rs` as expected, and passes after that file was fixed.
- **`website/build.py` emitted dead permalinks.** It now refuses a GitHub link whose target is
  absent from the pinned commit or whose bytes differ from it. The dirty-tree refusal was not
  weakened to make a build pass. Across 8 editions, 2,540 pinned links were checked with
  `git cat-file` and none was absent.
- **Non-atomic JAR downloads** in `postgres/fetch_jdbc.py` (fixed: temp file in `.deps/` then
  rename) and `http/fetch_json.py` (in flight).
- **`postgres/verify.py` printed hardcoded counts.** Now computed with `len(...)`. They happen
  to equal the old literals, which is the honest outcome to report.
- **`roo-track.yml` ran twice per push when a pull request was open.** `push` is now limited to
  `main`, matching the other workflows, plus a `concurrency` group that cancels superseded
  pull-request runs but never cancels a run in flight on `main`, so merged commits keep their
  hosted qualification.
- **`docs.yml` did not rebuild when a linked source file moved.** A simulation found 95 linked
  repository files uncovered by the old filters and 0 after widening them.
- **`website/pages/index.md` `#try-it`** resolved on the generated site but not on GitHub. Now
  both, via an explicit anchor element before the heading.

### Evidence receipts no longer overwritten by local runs

A problem the earlier fix round introduced itself: running the verifiers locally overwrote the
dated, tracked receipts under `research/`. Both verifiers now accept `--evidence-output PATH`
and a `ROO_EVIDENCE_PATH` environment variable, the flag winning over the variable, with the
destination validated *before* the long run so an unusable path fails in a second rather than
after three minutes. The new CI workflow gives each phase its own path.

The two differ in what happens when you name nothing, and the difference is deliberate.
`http/verify.py` writes only an untracked scratch receipt, which is what `main` did and what
section 8 item 6 restores. `postgres/verify.py` keeps refreshing its historical receipt,
because that is `main`'s long-standing behaviour and it writes no scratch receipt to fall back
to. Section 10 records why that asymmetry was left rather than quietly changed.

- **Stale counts replaced with measured ones**, and the dated historical counts kept as the

  from 280. The three negative-compilation samples are documented as a table with each sample's

## 8. Problems found *in the fix work itself*

Reviewing the agents' diffs rather than their summaries caught five things.

1. **A snapshot bug that would have broken every hosted run.** The reference workflow's
   PostgreSQL version guard tested for `*"PostgreSQL 18."*`, which never matches the real
   output `postgres (PostgreSQL) 18.6 ...`. Corrected to `*"(PostgreSQL) 18."*` and confirmed
   locally. Had the snapshot been ported verbatim, CI would have failed on every run.
2. **A runner label that would have silently disabled the new workflow.** The new workflow
   arrived on `ubuntu-26.04`, a label no other job in the repository uses and that actionlint
   does not recognise. I sent it back rather than tolerating the warning, because a
   non-existent label means the job never runs at all — the worst failure mode for a workflow
   whose whole purpose is to close the "no CI runs the verifiers" gap. The resolution turned
   out better than either option: the workflow now runs on `ubuntu-24.04` and installs
   PostgreSQL 18 explicitly from PGDG, so it no longer depends on the runner image's version.
   `actionlint` is now **completely clean**, where the earlier round had one tolerated warning.
3. **A documentation change that would have enshrined a defect.** The snapshot "fixed" the
   `EventId`-only deduplication divergence by *documenting* it in
   `adoption/relationship-contract.md:85`. Meanwhile a sibling front was closing it in code. I
   stopped the documentation port; the existing wording is now true of all three
   implementations.
4. **A claim worth checking rather than accepting.** The CI front removed `src/**`,
   `examples/**`, `templates/**` and `Cargo.*` from the track triggers, arguing the Docker
   context excludes them. I verified it: `.dockerignore` excludes `**` and re-includes only
   `case-studies/orders-payments/**`, and the Dockerfile's single source copy is
   `COPY --chown=roo:roo case-studies/orders-payments/ case-studies/orders-payments/`. The
   argument holds.
5. **Cross-front staleness the owning fronts could not see.** Three files became wrong because
   of a *sibling's* change, and were routed to their owners: the case-study README's
   "two negative examples" paragraph, `track/SPEC.md:76`'s "Rust's common guarantee is ID
   deduplication", and the Java unit-check count.

6. **A regression introduced by the fix itself, caught at the end.** The HTTP front ported
   the evidence-redirection interface from its PostgreSQL sibling, including that sibling's
   *default*: write the receipt to the tracked historical file
   `research/http-integration-evidence.json` unless redirected. But `main`'s
   `http/verify.py` wrote **only** to an untracked `.runtime/` log and never touched
   `research/` at all. So the port made every local verifier run overwrite a dated, tracked
   receipt — which is precisely the hazard the earlier verification round had flagged as a new
   side effect, now reintroduced.

   The front's stated reason was symmetry with PostgreSQL. Symmetry with a hazard is not a
   virtue, least of all in a repository whose entire P2 section is about not corrupting
   historical evidence. The repository's own `http/regression.py` exists for no other purpose
   than to run the PostgreSQL qualification "without replacing its old receipt", which settles
   what the intended behaviour is.

   **Fixed by restoring `main`'s default.** A plain run now writes only the untracked scratch
   receipt; `--evidence-output` and `ROO_EVIDENCE_PATH` add a second copy when asked, the flag
   winning over the variable, with the destination validated before the long run starts. CI is
   unaffected because it names a distinct path per phase. Verified by capturing the tracked
   receipt's SHA-256, running the full 200-second verifier with no variable set, and confirming
   the hash was byte-identical afterwards: `056ef224…` before and after.

Two smaller items I noted for cleanup rather than sending back: `website/build.py:prepare()`
reuses the name `kind` for the edition kind and then the git object kind three lines later
(functionally correct, since the verification runs before the reassignment, but confusing in
new code), and `configure_output` mutates module globals where the repository's style rule
prefers immutability.

## 11. Limits of this work — what it does not establish

- **No hosted CI run has happened.** The new workflow is lint-clean and its PostgreSQL
  selection and JDK guard steps were executed locally, but the scripts were never run
  end to end on a GitHub runner. Hosted execution is unverified.
- **The local JDK is 26, not the CI's 21.** The Java examples compile at release 21, but
  nothing here certifies behaviour under an actual JDK 21 runtime.
- **This is not independent human review.** It is AI review plus local deterministic
  qualification. It is not an efficacy experiment for the method the repository documents.
- **Historical evidence gaps remain gaps.** A test run today does not retroactively supply
  evidence for a run recorded in 2026-10-11. The P2 work makes the gaps explicit; it does not
  fill them.
- **Earlier failures were preserved, not erased.** Where a check failed before a fix, the
  failure stands in the record and the passing result is dated after it.
- **Nothing has been pushed.** No commit, push, merge, rebase, tag, release or deploy was
  performed against any remote.
